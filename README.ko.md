# AlphaEvolve Plugin

[English](README.md) | **한국어**

Google DeepMind의 **AlphaEvolve**와 오픈소스 **OpenEvolve** 구조를 따라 만든 진화형 알고리즘 탐색·코드 최적화 플러그인입니다.
Claude Code와 Antigravity에서 쓸 수 있습니다.

## 설치

**Claude Code**
```
/plugin marketplace add bakeyeon/alphaevolve-plugin
/plugin install alphaevolve@alphaevolve-plugin
```

**Antigravity**: 저장소를 플러그인으로 추가하면 됩니다. 루트의 `plugin.json`을 사용합니다.

## 주요 기능

1. **에이전트 기반 진화 루프 (Mode A)**
   - 별도 패키지나 API 키 없이 에이전트가 직접 변이를 제안합니다.
   - `evolve_local.py`가 후보를 평가하고 `archive.json`과 `best_program.py`를 관리합니다.
   - 명령은 `init`, `sample`, `evaluate`, `status` 네 가지입니다.
2. **OpenEvolve CLI 연동 (Mode B)**
   - `pip install openevolve`와 바로 호환되는 `initial_program.py`, `evaluator.py`, `config.yaml`을 만듭니다.
3. **믿을 수 있는 평가기 템플릿**
   - 정답 기준(정확한 DP)과 비교해 정확성을 판정합니다.
   - 시드를 고정한 무작위 인스턴스 40개와 경계 사례로 테스트하며, 최종 검증용 `--held-out` 분리 세트를 지원합니다.
   - 후보마다 별도 프로세스에서 시간 제한과 코드 길이 상한(`MAX_CODE_CHARS`)을 두고 실행합니다.
   - 점수(`combined_score`)는 항상 같은 값이 나오게 품질만 반영합니다. 실행 시간은 중앙값으로 따로 기록합니다.
4. **비공개 코퍼스 및 GDPR 보호 (`BLIND_MODE = True` 기본 적용)**
   - 에러 메시지 원문, 후보의 `print`/`stderr` 출력, 실제 데이터 값을 자동으로 마스킹하여 코퍼스 문장이나 참여자 정보가 클라우드 에이전트 컨텍스트로 유출되지 않게 막습니다.

## 내 문제에 이 플러그인이 맞을까?

프로그래밍을 몰라도 됩니다. 문제를 평소 말로 설명하면 에이전트가 코드와 채점 스크립트를 만들고 루프를 돌립니다.
여러분이 가져올 것은 도메인 지식입니다. 어떤 답이 좋은 답인지, 어떤 답은 허용되지 않는지를 알려 주면 됩니다.

**한 줄 요약.** 여기서 말하는 진화는 "레시피를 여러 가지로 바꿔 보고, 하나씩 맛보고, 제일 나은 걸 남기는 일을 반복"하는 것입니다.
맛보기가 자동으로, 빠르게, 공정하게 되어야만 통합니다. 그래서 세 가지를 물어보세요.

1. **서술형이 아니라 OMR 객관식 시험처럼 기계가 채점할 수 있나요?** 채점은 세기, 재기, 비교하기만으로 해야 합니다. 사람의 판단이 들어가면 안 됩니다.
2. **채점하면서 답이 규칙을 지키는지도 확인할 수 있나요?** (규칙 위반이 없다, 믿을 수 있는 느린 버전과 결과가 같다)
3. **채점 한 번이 몇 시간이 아니라 몇 초 안에 끝나나요?** 진화는 수십에서 수백 번 시도합니다.

셋 다 "예"면 이 플러그인이 잘 맞습니다. 하나라도 "아니오"면 보통 더 간단한 방법이 낫습니다.

### "기계가 채점할 수 있다"는 게 무슨 뜻인가요

| 문제 | 채점 방법 | 하는 일 |
|---|---|---|
| 96웰 플레이트 샘플 배치 | 같은 샘플의 반복이 같은 플레이트에 들어간 쌍을 센다. 0이면 만점 | 세기 |
| 공용 장비 예약 | 모든 요청의 대기 시간을 더한다. 작을수록 좋음 | 재기 |
| 느린 전처리 함수 | 스톱워치로 시간을 재고, 원래 함수와 출력이 같은지 확인 | 재기, 비교하기 |
| 분류 규칙 | 정답이 달린 예시 500개에서 맞힌 개수를 센다 | 세기, 비교하기 |
| 학습 배치 묶기 | 채워 넣은 패딩(빈칸) 수를 센다 | 세기 |

기계가 채점하기 어려운 것: "이 그림이 보기 좋은가?", "이 초록이 설득력 있는가?", "이 가설이 새로운가?"
사람마다 점수가 다르고, 같은 사람도 내일은 다르게 줄 수 있습니다.

**확인해 보기: 규칙을 코드로 짤 수 있나?** 에이전트에게 이렇게 물어보세요.
*"이 채점 규칙을 파이썬 함수로 짜 줘. AI 호출이나 사람 판단 없이, 세기·재기·비교하기만 써."*
짤 수 있으면 기계가 채점할 수 있습니다. 함수 안에 "AI에게 물어본다"나 "적절한지 판단한다" 같은 단계가 필요하다면 못 합니다.
어차피 진화 루프에 필요한 게 바로 이 스크립트라서, 이게 가장 직접적인 테스트입니다.

*사고실험:* 이 규칙을 조교 두 명에게 넘겼다고 상상해 보세요. 둘이 언제나 같은 점수를 낼까요? 아니라면 규칙이 아직 애매한 겁니다.

*에이전트 두 개는 경고 신호로만:* 같은 규칙과 같은 예시 답을 서로 다른 에이전트 세션 두 개에 줘 볼 수 있습니다.
점수가 다르면 규칙이 애매하다는 뜻입니다. 같다고 해서 증명은 아닙니다. 같은 모델은 생각하는 방식이 비슷해서
"이 초록이 설득력 있나?" 같은 애매한 질문에도 같은 점수를 줄 수 있습니다.

**애매한 목표는 셀 수 있는 조각으로 쪼개세요.** "좋은 실험 설계인가?"는 그대로는 채점할 수 없지만 조각은 됩니다.
조건마다 샘플 수가 같은지(차이를 센다), 대조군이 날짜별로 고르게 퍼졌는지(치우침을 잰다), 총 비용이 예산 안인지(비교한다).

AI에게 "1점에서 10점으로 평가해"라고 시킬 수도 있지만, 점수가 들쭉날쭉하고 진화가 문제를 푸는 대신 AI 채점자의 비위를 맞추는 쪽으로 흐르기 쉽습니다. 주 점수로는 쓰지 마세요.

### 잘 맞는 경우: 작업

| 분야 | 쉬운 말로 한 문제 | 점수 | 꼭 지켜야 할 규칙 |
|---|---|---|---|
| 실험 생물학 | 반복 샘플과 대조군이 고르게 퍼지도록 96웰 플레이트에 샘플 배치 | 제약 위반 수가 적고 균형이 좋을수록 | 모든 샘플이 정확히 한 번 배치 |
| 심리학 | 참가자마다 자극 순서를 정해 어떤 항목도 늘 앞이나 뒤에 오지 않게 하기(역균형화) | 위치·순서 치우침 | 모든 참가자가 모든 항목을 한 번씩 봄 |
| 모든 실험실 | 공용 장비(시퀀서, 현미경) 예약 요청 여러 건 배정 | 총 대기 시간 | 중복 예약 없음, 마감 준수 |
| 언어학, NLP | 큰 말뭉치에서 너무 느린 텍스트 정제·토큰화 함수 | 고정 샘플에서 실행 시간 | 지금 함수와 출력이 똑같음 |
| 생물정보학 | 파이프라인의 병목인 직접 만든 서열 점수 함수 | 실행 시간, 메모리 | 원래 함수와 점수가 같음 |
| 운영, 물류 | 현장 조사 방문지나 배송 경로 짜기 | 총 이동 거리 | 모든 장소 방문, 시간대 준수 |
| ML 학습 | 길이가 제각각인 시퀀스를 패딩이 최소가 되도록 배치에 묶기 | 패딩 비율, 에폭당 배치 수 | 모든 시퀀스 한 번씩 사용, 배치 크기 제한 |
| ML 학습 | 데이터 전처리 단계나 직접 만든 레이어 하나 빠르게 하기 | 고정된 작은 입력에서 실행 시간과 최대 메모리 | 기준 코드와 출력이 같음 |

**대규모 학습 코드.** 학습 전체를 진화시킬 수는 없습니다. 평가 한 번에 몇 시간씩 걸리기 때문입니다.
대신 느린 부분 하나(전처리 단계, 배치 묶는 규칙, 직접 만든 연산 하나)를 떼어 내고, 고정된 작은 입력을 주고,
결과가 같은지 확인하면서 속도와 메모리를 몇 초 안에 채점합니다. 평가기 템플릿은 실행 시간을 잽니다.
메모리는 에이전트에게 최대 메모리 지표를 추가해 달라고 하세요(예: `tracemalloc`, GPU라면 `torch.cuda.max_memory_allocated`).
그다음 개선된 부분을 전체 학습 코드에 다시 넣고 실제로 빨라졌는지 확인합니다.

### 잘 맞는 경우: 데이터에서 규칙을 찾는 연구 실험

진화로 설명을 찾을 수도 있습니다. 데이터를 재현하는 작고 읽을 수 있는 프로그램(규칙 목록, 공식, 간단한 시뮬레이션)을 찾는 것입니다.
그 프로그램이 곧 가설이고, 직접 읽어 볼 수 있습니다. 이게 통하려면 원칙이 하나 있습니다.

**프로그램이 보지 못한 데이터로만 채점하세요.** 데이터 일부를 시기나 항목 기준으로 떼어 두고, 그 부분으로만 채점합니다.
그러지 않으면 진화가 데이터를 외워 버려서 점수가 아무 의미가 없습니다. 아직 오지 않은 미래로는 예측을 채점할 수 없으니,
과거의 어느 해를 "지금"이라고 치고 그 뒤에 실제로 일어난 일과 비교해 채점합니다(백테스팅이라고 합니다).

**예시: 언어 변이가 어떻게 갈라지고, 앞으로 어디로 갈까?**
질문을 채점할 수 있는 형태로 바꾸면 됩니다. 두 가지 방식이 있습니다.

1. **음운 변화 규칙.** 데이터: 옛 어형과 여러 방언에서 실제로 쓰이는 어형.
   진화시킬 것: 옛 어형을 각 방언 어형으로 바꾸는, 순서가 있는 음운 변화 규칙 목록.
   채점: 학습에서 떼어 둔 단어들에서 예측 어형과 실제 어형이 몇 글자 다른지(편집 거리).
   규칙: 일반적인 음운 규칙만 허용하고 단어별 예외는 금지합니다. 그래야 프로그램이 정답을 외워 두지 못합니다.
   얻는 것: 방언마다 그럴듯한 규칙 순서, 그리고 규칙을 따르지 않는 단어들(차용어일 가능성).
2. **변이형 사용의 추이.** 데이터: 경쟁하는 변이형(예: 두 가지 어미)이 시기·지역별로 얼마나 쓰였는지(말뭉치나 설문).
   진화시킬 것: 변화의 작은 모형. 공식일 수도 있고, 이웃과 권위 있는 형태를 따라 하는 화자들의 시뮬레이션일 수도 있습니다.
   채점: 1950-1990년 데이터로 맞추고 2000-2020년을 예측해 실제 관측과의 오차를 잽니다.
   그다음 가장 좋은 모형을 앞으로 돌려 추이를 전망합니다.

| 분야 | 진화시킬 것 | 떼어 둔 데이터로 채점 |
|---|---|---|
| 언어학 | 단어 목록으로 화자의 방언을 맞히는 규칙 | 떼어 둔 화자들에서 정확도 |
| 생태학 | 날씨를 입력으로 받는 개체 수 증가 규칙 | 이후 연도 개체 수 예측 오차 |
| 역학 | 단기 환자 수 예측 규칙 | 과거 몇 주에 대한 백테스트 오차 |

결과를 쓸 때 꼭 밝혀 둘 한계:
- **잘 맞는다고 원인이 증명되진 않습니다.** 서로 다른 여러 프로그램이 똑같이 잘 맞을 수 있습니다. 1등만 보지 말고 상위 몇 개를 비교하고, 도메인 지식으로 판단하세요.
- **데이터가 적으면 과적합되기 쉽습니다.** 프로그램을 작게 유지하고 떼어 둔 데이터는 건드리지 마세요.
- **멀리 내다볼수록 예측은 불확실해집니다.** 사실이 아니라 시나리오로, 백테스트 오차와 함께 보고하세요.

### 굳이 안 써도 되는 경우

| 상황 | 진화가 도움이 안 되는 이유 | 대신 쓸 것 |
|---|---|---|
| 이미 방법이 알려진 표준 작업(정렬, 최단 경로, 선형 회귀, 서열 정렬) | 전문가들이 이미 최선의 방법을 찾아 둠 | 기존 라이브러리. 어떤 걸 쓸지 에이전트에게 물어보세요 |
| 숫자 몇 개 조정(학습률, 임계값) | 코드가 아니라 숫자를 찾는 문제 | 그리드 탐색이나 Optuna 같은 튜너 |
| 효과가 진짜인지 검정(A 집단과 B 집단 비교) | 탐색이 아니라 통계 문제 | 표준 통계 검정 |
| 자동 점수가 없음(글의 완성도, 그림 디자인, "이 가설이 흥미로운가") | 시도끼리 비교할 기준이 없음 | 에이전트에게 바로 묻고 직접 판단 |
| 평가 한 번에 몇 분에서 몇 시간(학습 전체, 밤새 도는 시뮬레이션, 실제 실험) | 수백 번 시도하면 몇 주가 걸림 | 먼저 빠른 축소 문제로 바꾸거나 직접 최적화 |
| 코드가 틀리거나 멈춤 | 진화는 돌아가는 코드를 개선할 뿐 버그를 고치지 않음 | 에이전트에게 버그 수정 요청 |
| 한 번만 돌릴 스크립트 | 몇 초 아껴도 의미 없음 | 돌아가는 가장 간단한 버전 |

### 프로그래밍을 몰라도 시작하는 법

1. 문제를 설명합니다: *"샘플 300개를 96웰 플레이트에 배정해. 같은 샘플의 반복은 같은 플레이트에 두면 안 되고, 플레이트마다 대조군이 4개 필요해. 플레이트끼리 최대한 균형 있게 해 줘."*
2. 에이전트가 단순하고 확실히 맞는 버전(L1)과 채점 스크립트를 만듭니다.
3. **채점 스크립트는 직접 확인하세요.** 예시 답 몇 개와 점수, 규칙 검사 결과를 보여 달라고 하고, 규칙을 코드로 짤 수 있는지 물어보세요. 나쁜 답이 좋은 점수를 받으면 알려 주세요. 진화는 점수만 쫓아갑니다.
4. Mode A 루프를 돌리고, `best_program.py`와 점수 기록을 에이전트와 함께 읽습니다.

## 비공개 데이터·코퍼스 보호 (GDPR / IRB 대응 기본 적용)

AlphaEvolve 구조는 **코드를 짜는 AI**와 **데이터를 채점하는 로컬 평가기(`evaluator.py`)**가 분리되어 있어서, 클라우드 AI에게는 코퍼스 원문을 보여주지 않고 파이썬 코드와 집계 점수만 주고받으며 진화시킬 수 있습니다.

에러 메시지나 디버그 출력으로 코퍼스 원문이 새어나가는 것을 막기 위해, `evaluator.py`에는 **`BLIND_MODE = True`가 기본값(Default)으로 켜져 있습니다**:
- **에러 메시지 원문 마스킹**: 후보 코드가 크래시날 때(예: `KeyError('민감한_발화문')` 등) 예외 메시지 문자열과 `stderr`를 모두 제거하고, **예외 종류와 줄 번호(`KeyError at candidate.py:24 in solve`)만** 에이전트에게 돌려줍니다.
- **`print` 출력 완전 차단**: 후보 코드가 데이터를 `print()`하더라도 결과가 에이전트에게 전달되지 않습니다.
- **집계 지표만 반환**: 제약 위반 시에도 실제 데이터 값 대신 몇 번째 케이스에서 어떤 규칙을 어겼는지만 리포트합니다.

**민감 데이터(유럽 GDPR·DSGVO / 대학 IRB 코퍼스 등) 실험 시 4단계 수칙:**
1. **데이터를 넣기 전에 민감정보(PII)부터 미리 마스킹·가명화하기**: 로컬에서 평가하더라도, 실험 전처리 단계에서 참여자 실명, 고유 ID, 연락처, 세부 주소나 특정인을 알아볼 수 있는 발화 내 고유명사는 반드시 `SPK_001`, `[NAME]`, `[LOC]` 등으로 **미리 마스킹(가명화)**한 뒤 투입하세요.
2. **에이전트에게는 3줄짜리 가짜 더미 파일(`dummy_sample.tsv`)만 보여주기**: 실제 코퍼스는 작업 폴더 바깥에 두거나 에이전트 읽기 권한(`.claude/settings.json`의 `permissions.deny`)으로 막고, 컬럼 구조만 똑같은 가짜 예시 3줄만 프로젝트에 넣어줍니다.
3. **`evaluator.py`의 `BLIND_MODE = True` 유지하기**: 실제 채점은 로컬의 `evaluator.py`가 비공개 경로의 파일을 읽어서 수행하고, 에이전트에게는 점수 숫자만 돌려줍니다.
4. **100% 완전 오프라인(Air-gap)이 필요하다면**: Mode B(`openevolve`)의 `config.yaml`에서 `api_base: "http://localhost:11434/v1"`로 로컬 LLM(Ollama, LM Studio, vLLM)을 연결하면 인터넷 연결 없이 랩탑 안에서만 돌아갑니다.

## 추천 흐름: 3단계 다음에 진화

1. **L1 기본**: 정의를 그대로 옮긴, 확실히 맞는 코드. 평가기의 정답 기준이 됩니다.
2. **L2 깔끔**: 읽기 좋고 실용적인 알고리즘
3. **L3 최적**: 직접 유도할 수 있는 가장 좋은 방법
4. **진화**: L3보다 더 나은 답을 탐색하고 싶을 때만 씁니다. 점수를 코드로 계산할 수 있는 문제여야 합니다.

## 로컬 진화 코드 한눈에 보기

Mode A에서는 스크립트 세 개가 일을 나눕니다. `scaffold_evolve.py`는 작업 폴더를 한 번 만들고,
`evaluator.py`는 프로그램 하나를 채점하고, `evolve_local.py`는 모든 시도의 기록을 남기며 어느 것이 최고인지 정합니다.
새 프로그램은 에이전트가 쓰고, 이 스크립트들은 판정과 기록만 합니다.

**`scaffold_evolve.py`**
- `scaffold(target_dir, task_name)`: 템플릿 파일 네 개를 새 작업 폴더에 복사하고 `candidates/`를 만듭니다. 이미 있는 파일은 건너뛰어서 직접 고친 내용을 덮어쓰지 않습니다.

**`evaluator.py`**
- `make_instances(seed, n)`: 테스트 세트를 만듭니다. 시드를 고정한 무작위 문제 n개와 정해진 경계 사례입니다. 시드가 같으니 모든 후보가 같은 문제로 시험받습니다.
- `reference_solve(items, capacity)`: 진짜 최적값을 주는 믿을 수 있는 느린 풀이(정확한 DP)입니다.
- `evaluate(program_path, held_out=False)`: 코드 길이 상한(`MAX_CODE_CHARS`, 답 외우기 테이블 방지)을 먼저 확인하고, 후보를 별도 프로세스에서 시간 제한을 두고 실행하며, 규칙을 어긴 답이 하나라도 있으면 탈락시키고 지표를 돌려줍니다: `combined_score`, `valid`, `split`, `optimality_ratio`, `optimal_fraction`, `runtime_ms`, `complexity`. `held_out=True`(또는 CLI에서 `--held-out`)를 넘기면 진화 동안 쓰지 않은 `HELD_OUT_SEED` 데이터로 일반화 성능을 검증합니다.
- `_fail(error)`: 탈락한 후보의 지표입니다(점수 0, `valid` 0, 탈락 이유).

**`evolve_local.py`** (명령)
- `init` (`cmd_init`): `initial_program.py`를 `gen_000`으로 채점하고 새 `archive.json`을 시작합니다.
- `sample` (`cmd_sample`): 다음에 변형할 부모를 추천합니다. 최고 점수 후보들(exploit)과 크기가 다른 프로그램 최대 두 개(explore)를 함께 줘서 한 아이디어에 갇히지 않게 합니다.
- `evaluate` (`cmd_evaluate`): 새 후보를 `candidates/`에 복사해 채점하고, 부모와 변경 이유와 함께 기록하고, `delta_vs_parent`를 알려 줍니다(양수면 변경이 도움이 됨).
- `status` (`cmd_status`): 최고 세대와 모든 세대의 한 줄 기록을 보여 줍니다. 진화가 끝난 뒤 `--held-out` 옵션을 붙이면 `best_program.py`의 미공개 데이터 검증 지표(`held_out_metrics`)를 함께 출력합니다.

**`evolve_local.py`** (보조 함수)
- `load_evaluator(workspace)`: 작업 폴더에 있는 `evaluator.py`를 불러옵니다.
- `load_archive` / `save_archive`: `archive.json`을 읽고 씁니다.
- `_update_best(workspace, archive)`: 점수가 가장 높은 유효한 세대를 찾아 `best_program.py`로 복사합니다. 점수가 같으면 먼저 나온(보통 더 단순한) 프로그램이 이깁니다.
